# 開發日記：餵小怪獸是怎麼做出來的

2026-10-10

這份日記記錄「餵小怪獸」從空專案做到可以給小學生試玩的過程。開發方式是開發者與 AI coding 工具（Claude Code）一來一往合作完成：開發者做決定、在 Unity 裡試玩和實機測試，AI 負責分析、寫程式與更新文件。

寫給之後接手的新人。目的不只是說明程式長什麼樣子（那些看 [QuestionModule.md](QuestionModule.md) 和程式碼就知道），而是說明**每一步為什麼這樣做、在哪裡卡住、怎麼發現的**。

> 花費時間由開發者填寫，彙整在 [Prototype.md](Prototype.md) 的「開發紀錄」表格。

---

## 起點

- Unity 6（6000.6.4f1）URP 空範本，只有 `SampleScene`，沒有任何遊戲程式碼。
- Input System、UGUI、Test Framework 已經裝好，專案設定為只用新版 Input System。
- 三份文件：
  - `CLAUDE.md`：程式規範（不用 Singleton、用 `Awaitable` 不用 Coroutine、規則放一般 C# 類別……）
  - `Docs/Prototype.md`：企劃、範圍（要做／不做）、里程碑
  - `Docs/QuestionModule.md`：答題模組的介面草案與 eMath API 整理
- 參考專案 `../MathQuestionGame`，只能看題目格式與 API，不能複製程式碼。

**心得：先寫文件再開工，是這次能做得快的主因。** AI 每一步都以這三份文件為準，範圍和寫法不需要一再重複說明。

## 第 0 步：分析任務，先把問題問清楚

第一個指令是「先讀 Docs，分析本次任務」，沒有直接叫 AI 寫程式。

AI 讀完文件、看過專案與參考專案之後，列出了文件**沒寫清楚、但會影響實作**的地方：

| # | 問題 | 決定 |
| --- | --- | --- |
| 1 | Android 的 StreamingAssets 包在 apk 裡，`System.IO` 讀不到 | 請 AI 規劃做法 → 一律用 `UnityWebRequest` 讀 |
| 2 | 斷網時線上取題可能卡住很久 | 加逾時；沒網路就直接不打 API |
| 3 | API 的 `answer` 從 0 還是從 1 起算 | 決定「從 0」 ⚠️ 後來證明是錯的，見里程碑 1 |
| 4 | 開始畫面只選年級，但取題需要出版社 | 固定用子由 |
| 5 | 離線題庫只有一兩個年級，但開始畫面有 12 個年級 | 離線題庫涵蓋所有年級 |
| 6 | 離線題庫用 API 下載，還是從舊專案轉換 | 用 API 下載（舊專案的格式依賴 Odin，不一定解得開） |

另外也發現專案資料夾還不是 git repo，所以文件要求的「Token 放進 `.gitignore`」其實不會生效。

**心得：** 這一步只花幾分鐘，卻擋下了好幾個寫完才會發現的坑。給新人的建議：**先叫 AI 分析、列出疑點，自己做完決定，再叫它動手。**

## 里程碑 1：答題模組

**花費時間：**（請填）

### 做了什麼

- `Assets/MathQuestion/`，有獨立的 `MathQuestion.asmdef`。遊戲端只看得到 `QuestionProvider`、`Question`、兩個題目來源和 `EMathConfig`，其餘（API 呼叫、序號計算、題庫格式）都是 `internal`。
- `QuestionProvider` 先取線上題目，不足時用本機題庫補，並依題目 `Id` 去重。
- 斷網處理：
  - 系統回報沒網路時，直接不打 API。
  - 每個請求 5 秒逾時。
  - 連線錯誤或 Token 被拒時，停止線上取題，已經取到的題目保留。
- 本機題庫的下載工具：選單 Tools → Math Question → 下載本機題庫。
- Token 放在 `Assets/Config/EMathConfig.asset`，已加進 `.gitignore`。
- EditMode 測試：序號計算、`IsCorrect`、線上不足時用本機補、本機題庫讀取。

### 卡住的地方

**1. Unity 編輯器開著，AI 沒辦法用 batchmode 編譯或跑測試**

同一個專案不能同時被兩個 Unity 開啟。AI 改用 dotnet 搭配 Unity 的 DLL，在暫存資料夾單獨編譯，至少確認沒有編譯錯誤；測試則由開發者在 Test Runner 裡跑。之後每個里程碑都沿用這個做法。

**2. `answer` 的起算方式判斷錯誤（這次最重要的一課）**

第 0 步決定了「answer 從 0 起算」，但當時沒有實際資料可以確認。開發者第一次跑下載工具後，AI 檢查下載到的 43 題，發現：

- 沒有任何一題的 `answer` 是 0。
- 有 13 題的 `answer` 等於選項數（例如 4 個選項、answer = 4）。

AI 接著打開其中一題的圖片人工驗算：9 − 5 = 4，但選項寫甲是 3，乙、丙也都不對，正解是 ④「以上都不對」，跟 answer = 4 一致。所以 **answer 是從 1 起算**。如果沒發現，遊戲裡每一題的正確答案都會被往後推一位。

**心得：拿不準的事，要用真實資料驗證，不要靠推測定案。** AI 能讀圖片，請它直接看資料比對，比讓它推測可靠得多。

**3. 下載工具遇到一次逾時就整批中斷**

下載工具一開始用了給遊戲的 5 秒逾時，而且逾時一次就整批停止，所以只下載到五上。修正如下：

- 下載工具的逾時改為 30 秒。
- 連續失敗 3 次才中斷。
- 中斷時，已經下載的題目一定會寫進 `index.json`。

### 順帶確認的事

- 同一個序號重複請求，會隨機回傳不同的題目，所以一次取 1 題、重複請求是有意義的。
- 圖片每張約 17 KB，所有年級加起來不到 10 MB。原本依舊專案估計約 50 MB。
- 圖片實際上是 JPEG，但存成 `.png` 副檔名。`Texture2D.LoadImage` 會依內容判斷格式，所以不影響。

## 里程碑 2：遊戲畫面（拖曳與對錯）

**花費時間：**（請填）

### 做了什麼

- `QuestionRound`（一般 C# 類別）：出題順序、答錯留在同一題、「第一次就答對」的計數。有單元測試。
- `FoodItem`：用 UGUI 的 `IBeginDragHandler`／`IDragHandler`／`IEndDragHandler` 拖曳。
- `MonsterView`：張嘴、吃、吐的反應。沒有美術素材，先用嘴巴大小、顏色和晃動表示。
- `GameScreen`：顯示題目、依選項數量排食物、判斷放開的位置。
- `Tween`：用 `Awaitable` 寫的簡單逐格動畫，沒有引入補間套件。

### 關鍵決定：用程式產生場景

UI 不是手動在編輯器裡拉，而是寫了一個編輯器工具（Tools → Game → 建立遊戲場景）來產生整個場景，包含所有 Inspector 參照。

- **好處：**
  - AI 沒辦法操作 Unity 編輯器，但可以寫產生場景的程式。
  - 改版面時只要改數值、重建就好。
  - 參照不會漏拖。
- **代價：** 手動在場景裡調整的東西，重建時會被覆蓋。要保留的調整，必須寫回產生器裡。

### 小設計

- 放開時的判定範圍是整隻怪獸，不只是嘴巴，讓小朋友比較容易放中。
- 同時間只允許拖一個食物，避免兩隻手指同時拖造成狀態混亂。

## 里程碑 3：一局流程與結果畫面

**花費時間：**（請填）

### 做了什麼

- 開始畫面（12 個年級按鈕排成 6 欄 × 2 列）、結果畫面（第一次就答對的題數、這局增加的飽足度、再玩一次、換年級）。
- 三個畫面放在同一個 Canvas 下輪流切換，不需要換場景。

### 關鍵決定：用 Awaitable 把流程寫成一段直線式的程式

每個畫面都回傳一個 `Awaitable`，在玩家按下按鈕或答完一局時才完成。所以 `GameEntry` 的主流程可以從上往下直接讀：

```csharp
var grade = await ChooseGrade();
while (true)
{
    _questions = await _provider.GetQuestions(...);
    await _gameScreen.Play(round);
    var choice = await _resultScreen.Show(...);
    if (choice == ResultChoice.ChangeGrade)
        grade = await ChooseGrade();
}
```

不需要狀態機，也不需要事件匯流排。這正是 `CLAUDE.md` 要求「用 async/await，不用 Coroutine」帶來的好處。

## 里程碑 4：怪獸成長與本機存檔

**花費時間：**（請填）

### 做了什麼

- `MonsterGrowth`：門檻 0／15／40 集中在一個地方。
- `PlayerProgress`：累積飽足度、目前階段、上次選的年級，用 `JsonUtility` 存成一筆 JSON 放進 `PlayerPrefs`。
- 遊戲畫面右上角有飽足度條；餵到門檻時怪獸當場長大，結果畫面也會顯示「長大了」。
- 三個階段暫時用大小（0.7／0.9／1.1 倍）表示。

### 關鍵決定

- **每餵一次就存檔，不是一局結束才存。** 小朋友常常玩到一半直接關掉 App。
- **階段另外存，而且只升不降。** 企劃說門檻是暫定值、試玩後會調。如果之後調高門檻，已經長大的怪獸也不會變小。

## 里程碑 5：平板實機與離線測試

**花費時間：**（請填）

### 卡住的地方

**沒有安裝 Android Build Support。** AI 檢查 Unity 的安裝目錄時發現只有 Mac 的建置支援，需要開發者在 Unity Hub 補裝模組。開始實機測試之前，記得先確認環境。

### 做了什麼

- 選單 Tools → Game → 套用平板設定：App 名稱、套件 ID、只允許橫向。同樣寫成選單，換電腦也能一鍵套用。
- 字型備案：把中文字型檔放進 `Assets/Game/Fonts/`，再重建場景就會取代內建字型。這次實機測試中文顯示正常，所以沒用上。
- 畫面更新率設為 60 FPS。Android 預設 30 FPS，拖曳會覺得卡。
- 整理了實機測試清單：有網路、飛航模式、有 Wi-Fi 但沒網路、存檔。

**結果：** 實機測試全部通過，包含離線完整玩一局。

## 總結：給新人的建議

### 和 AI 合作的方式

1. **先有文件，再開工。** 範圍（要做／不做）和程式規範寫清楚，AI 的產出才會一致，也比較不會自己加功能。
2. **先分析、再動手。** 第一個指令是「分析任務」，不是「開始寫」。
3. **決定由人來做。** AI 會列出選項和建議，但出版社、題庫範圍這類決定是開發者做的。
4. **不確定的事，用實際資料驗證。** `answer` 起算方式的錯誤，就是靠檢查下載下來的資料才抓到的。
5. **知道 AI 做不到什麼。** 它不能操作 Unity 編輯器、不能在編輯器開著時跑 batchmode、不能拿平板測試。這些事改由開發者做，或用「寫一個編輯器工具」的方式繞過。
6. **每個里程碑都要真的跑過一次。** AI 回報「編譯通過」不等於「可以玩」。每一步都由開發者在 Unity 裡試玩確認後，才進入下一步。

### 卡住的地方一覽

| 里程碑 | 問題 | 怎麼發現 | 解法 |
| --- | --- | --- | --- |
| 1 | 編輯器開著，不能用 batchmode 測試 | batchmode 回報錯誤 | 用 dotnet 單獨編譯；測試改在 Test Runner 跑 |
| 1 | `answer` 起算方式判斷錯誤 | 統計下載下來的資料，再看圖人工驗算 | 改成從 1 起算，並在文件記下驗證依據 |
| 1 | 下載工具逾時一次就整批中斷 | Console 的例外訊息 | 下載工具用較長的逾時，連續失敗 3 次才停，中斷前一定存檔 |
| 5 | 沒有安裝 Android 模組 | 檢查 Unity 安裝目錄 | 在 Unity Hub 補裝 |

## 接手時的第一步

1. 讀 `CLAUDE.md`、`Docs/Prototype.md`、`Docs/QuestionModule.md`，再讀這份日記。
2. 建立 `Assets/Config/EMathConfig.asset` 並填入 Token。沒有 Token 也能玩，只會用離線題庫。
3. 執行 Tools → Game → 建立遊戲場景，按 Play。
4. 打開 Test Runner，跑所有 EditMode 測試。
